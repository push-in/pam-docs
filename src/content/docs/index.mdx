## PHP beyond the request

PAM embeds PHP 8.4 through the official Embed SAPI and keeps your application alive. Rust owns the runtime boundary, Tokio schedules native I/O, and isolated PHP Fibers handle work without rebuilding the application for every request.

<CardGrid>
  <Card title="Server runtime" icon="seti:php">

  </Card>
  <Card title="Laravel" icon="rocket">
    Boot an unmodified Laravel 12 or 13 application once, isolate each request, and keep Artisan, queues, packages, and Composer familiar.

## Honest documentation, by design

PAM is ambitious and still experimental. Every guide separates what is implemented today from what is partial, planned, or deliberately unsupported.

<div class="status-grid">
  <div class="status-card"><strong>Available</strong><span>Implemented and covered by the current executable contract.</span></div>
  <div class="status-card"><strong>Experimental</strong><span>Usable for evaluation, but APIs or behavior may still change.</span></div>
  <div class="status-card"><strong>Planned</strong><span>Designed or scheduled, but not something you should depend on yet.</span></div>
  <div class="status-card"><strong>Help wanted</strong><span>A concrete place where a community contribution can move PAM forward.</span></div>

:::caution[Android today; iOS help wanted]
PAM Native and PAM Mobile UI currently target Android API 26–36. There is no iOS renderer yet. The protocol and ownership model were designed to allow another native renderer, and contributions toward iOS are especially welcome.
:::

## One ecosystem, not a replacement ecosystem

PAM does not replace PHP, Composer, Laravel, or PSR standards. It supplies a runtime beneath them and publishes optional first-party Composer packages above it. Start with the target that matches what you want to build.
